Professional Self-Assessment

How the program, and a prior career in financial services, shaped the way I build and explain software.

Before starting the Computer Science program at SNHU, I worked in financial services, mainly in banking and 401(k) administration. That background shaped a skill I rely on constantly as a developer: translating technical information into something a non-technical person can act on. I regularly explained financial products to clients with no finance background and turned vague requests into concrete next steps. That same instinct now shows up in how I write documentation, design API responses, and explain security decisions, making something technical understandable for whoever is on the other end.

My coursework was built around code reviews, peer feedback, and discussion-based learning rather than assigned team roles. That model still demanded the core skill of collaborative development: writing code clearly enough that someone else, a peer, an instructor, or a future employer, can follow my reasoning without me explaining it in person. My capstone reflects this directly: every enhancement below includes documentation, README context, and a narrative justifying why I made each choice, not just what changed.

My strongest data structures and algorithms work comes from enhancing Travlr Getaways, a travel booking app I originally built in CS 465. The original search relied on a linear scan through every trip for every query. For my enhancement, I built a Trie from scratch for prefix-based autocomplete, paired with an LRU cache using a hash map and doubly linked list to avoid repeated database hits. Building both without a library forced me to actually understand the trade-offs: memory versus speed, cache size versus hit rate, instead of just knowing the vocabulary.

My approach to software engineering and databases is best shown by how Travlr evolved across all three capstone enhancements, since each one built on the last. The software design enhancement restructured the app into proper layers: routes, controllers, services, validation, instead of mixing business logic with request handling. That restructuring is what made the algorithms enhancement possible without rewriting the app, since the new search logic dropped cleanly into the service layer. The database enhancement went further, replacing loosely typed schemas with validated Mongoose models, adding real relationships through Booking and Review collections, and using aggregation pipelines to calculate ratings instead of pulling every review into application code.

Security ran through all three enhancements rather than existing as a separate step. The original Travlr code passed user input straight into database queries, a textbook NoSQL injection risk. I addressed it with layered defenses: input validation and sanitization at the middleware level, schema-level validation as backup, and parameterized queries throughout. Coming from financial services, where a data error has real consequences, assuming input is hostile until proven otherwise was already familiar. CS 499 gave me the tools to actually implement it.

Together, these three artifacts tell one continuous story. Travlr started as functional but architecturally weak, and across software design, algorithms, and database work, it became something closer to what I'd actually ship. I'm presenting the original and enhanced versions side by side because the contrast is the point: this portfolio shows I can look at existing code critically and fix what's actually wrong with it. That's the core of backend development, not just building from scratch, but improving systems that already exist.

Software Design & Engineering

Restructuring a flat Express app into a layered architecture with validation and security built in.

Enhancement One

Travlr Getaways: Backend Architecture

v3.0 → v3.1

The original backend mixed route handling, business logic, and database queries inside the same controller functions, with no validation layer protecting against malformed or malicious input.

  • Separated routes, controllers, and services into distinct layers
  • Added request validation and sanitization middleware
  • Closed a NoSQL injection vulnerability in the original query handling
  • Documented architectural decisions in code comments and README

03

Algorithms & Data Structures

Replacing a linear scan with a Trie and an LRU cache, built from scratch rather than pulled from a library.

Enhancement Two

Travlr Getaways: Search & Caching

v3.1 → v4.0

The original search scanned every trip in the database on every query, with no caching for repeated lookups and no support for prefix-style autocomplete.

  • Built a Trie from scratch for prefix-based autocomplete search
  • Implemented an LRU cache with a hash map and doubly linked list
  • Dropped both directly into the existing service layer with no controller changes
  • Measured and documented the trade-offs between memory use and lookup speed

04

Databases

Replacing loosely typed schemas with validated models, real relationships, and aggregation pipelines.

Enhancement Three

Travlr Getaways: Schema & Data Layer

v4.0 → v5.0

The original MongoDB collections had minimal schema validation and no modeled relationships between trips, bookings, and reviews. Ratings would have required pulling every review into application code to average manually.

  • Added full Mongoose schema validation across all collections
  • Modeled real relationships with new Booking and Review collections
  • Built aggregation pipelines to calculate ratings inside the database
  • Parameterized all queries as a second layer of injection defense
